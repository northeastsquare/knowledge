00

先给结论

  1. 「所有工作」并不是同一类东西。 openpi 里能直接拿来跑的是 3 个模型（π0 / π0-FAST / π0.5）；而 KI 训练配方、π0.5 的异构共训、RTC、RECAP 都不在仓库里，需要自己补代码。真正的「改进项」大概 10 个，其中 7 个能在仿真里做干净的单变量消融，3 个基本只能做定性复现。
  2. 用默认设置跑 LIBERO 做消融是无效的。 π0.5 在 LIBERO 已经 96.9，天花板效应会把所有改进压成 ±1 个百分点、落在噪声里。要做归因，必须人为制造 headroom（少 demo、OOD 划分、延迟注入、遮挡探针），这是整个复现工程的成败点，不是细节。
  3. 仿真选型： LIBERO 做「对标锚点」，ManiSkill3 做「批量消融主战场」，RoboCasa 做「长时序/泛化验证」，Isaac Sim 只做最后一公里的真机前验证。不要用 Isaac Sim 跑算法消融。
01

把 openpi 的工作拆成可复现的三类

类别 内容 复现难度 说明
A · 开箱可复现 π0、π0-FAST、π0.5 的 base & 微调 ckpt；LIBERO 全流程（docker）；ALOHA sim 配置 低 官方给到 pi05_libero 配置 + serve_policy.py + LIBERO docker，跑通即可对标
B · 有权重无配方 π0.5 的 KI 预训练、异构共训（web VQA / caption / detection + 高层子任务）、RTC 的官方集成、MEM 中 只能评测，想训练得自己实现。openpi #649 明确说微调不走 KI 配方，动作专家梯度仍会进 VLM
C · 完全未开放 π0/π0.5 的 10k 小时预训练数据、真机结果、π*0.6 的 RECAP（价值函数 / 优势条件化）、真机部署 高 RECAP 只有论文 + 社区实现（LeRobot 有 PR、rlinf 有 openpi 分支），真机结果不可复现

这意味着什么

你能严谨测量的，是「在同一个 base ckpt 上、用同一份下游数据、微调之后的增量」。凡是论文里「收益来自 10k 小时预训练」的部分，你测不到——这一点必须在开始前写进实验设计，否则最后结论会误导人。

三个最容易踩的坑

它们直接决定你会不会得出「改进没用」的错误结论。

1

π0-FAST 在成功率上通常打不过 π0。 公开发表的 LIBERO 锚点：π0 94.2 / π0-FAST 85.5 / π0.5 96.9（Spatial / Object / Goal / Long 四套均值）。

FAST 的收益是训练吞吐和 tokenizer 通用性，不是最终成功率。你的归因表必须把「训练成本」和「成功率」分开画，否则会误判。

2

KI 的收益是收敛速度，不是峰值。 论文口径是 table bussing 上约 7.5× 更少步数、π0-FAST 完成时间约 2×。

所以指标应该是 steps-to-threshold（达到 80% 所需步数），而不是 20k 步的终点成功率。

3

π0.5 的收益只在 OOD 出现。 分布内就是 2 个点。不做 OOD 划分，你会得到「和 π0 差不多」的结论——这个结论是错的，但你的实验会这么告诉你。

为什么不用 Isaac Sim 做消融

哪怕仓库里已经有它：

  • 单任务 rollout 吞吐远低于 ManiSkill3 的 GPU 并行，而你需要的是「10 个消融项 × 3 个种子 × 每项数百 episode」的样本量；
  • USD 资产管线和 PhysX 接触参数调参成本，会全部变成混淆变量；
  • 渲染分布和 openpi 预训练数据（ALOHA / DROID / 仿真数据）差异大，需要额外增强，等于给每个消融项都加一个共同噪声源；
  • 它的价值在保真度和 ROS2 / Jazzy 部署链路——那正是仓库在做的事（CR5、perception heartbeat、DetectionStatus），放在最后一步做一次端到端验证最划算。

如果目标机是 CR5 单臂 + 夹爪

别去追 pi0_aloha_* 那几个双臂 ckpt，具身不匹配；走 pi05_base / pi05_droid + Franka 类仿真的路线更顺。

04

落地路线与算力

Phase 0（约 1 周）

先打通跑通 pi05_libero 官方 docker 闭环，复现出接近 94 / 97 的数字。这一步卡住的人非常多（norm stats、XLA 显存、docker 内 CUDA），先付这个成本。

关键工程决策

不要在 openpi 上开 10 个分支，做一个 fork + 特征开关。 否则每个消融项的差异里都混着数据管线、归一化、评测脚本的漂移，你的「增量」就不可归因了。

vla-ablation/
  third_party/openpi/          # submodule，只改 config + 模型层
  configs/ablation/
    base_pi0.yaml
    fast.yaml            # action_expert: ar_fast
    ki.yaml              # stop_grad: true, arch_tokens: fast, web_cotrain: true
    pis05_cotrain.yaml   # web_data: on, subtask_head: on, state: discrete
    rtc.yaml             # execution: rtc, latency_ms: 150
    recap.yaml           # advantage_conditioning: true
  eval/
    harness.py           # 统一 rollout：固定种子、逐 episode 记录、成对比较
    probes/              # language_following / occlusion_shortcut / vlm_retention

算力

按官方给的内存档：

  • 推理 > 8 GB
  • LoRA 微调 > 22.5 GB
  • 全量微调 > 70 GB
档位能做什么量级
单卡 24–40 GB 只能走 LoRA + 少量 demo，勉强做 #1 / #2 / #3 / #8 —
8×A100/H100 40 GB 起步，才能做全部 10 项的 3 种子矩阵 约 30 次训练 × 20k 步 + 评测 ≈ 4–6 天

省钱的做法

所有消融都用「少 demo」设定（每任务 10 条）+ 短训练（5k 步），让成功率落在 30–70% 区间——这个区间里改进的差异才看得见，而且训练成本降一个量级。

优先级（按信息量 / 成本比）

#3→ #1→ #8→ #4→ #2→ #6→ #5→ #7→ #10→ #9
#3（预训练 vs 从零）几乎一定是差距最大的一项；#9（MEM）需要自己造任务，收益测量成本最高，建议放最后或直接跳过。
05

评测协议

不做这一步，全部数字都不可信。

  1. 成对比较：所有策略在同一批初始状态 / 随机种子上评测（common random numbers），差值取配对样本。LIBERO 官方每任务 50 episode，10 任务 = 500 次，能检测的差异下限大概 3–4 个百分点；想判断 1–2 个点的差异，必须加大 episode 数或做配对。
  2. 固定执行协议：执行 chunk 的前 N 步要统一（很多人不统一，直接把 20 点差异归因给算法）。
  3. 报告三条曲线而不是一个数：成功率 vs 训练步数、成功率 vs 推理延迟、成功率 vs 注入延迟（RTC 专用）。
  4. 每个 ckpt 报 3 个种子，给 mean ± std；只报单次最好的结果，是这个领域通病。
  5. 把探针当一等公民：语言跟随、遮挡 shortcut、VLM 保留分——KI / π0.5 这类改进的收益在设计好的探针上才现形，在成功率上常常看不见。

如果是，建议把 #5 / #6 / #9 降级为「读论文即可」，把省下的算力投到 #3 / #4 / #8 + RoboCasa → Isaac Sim → 真机这条链上，产出更快落地。如果纯粹是想搞清每项改进的机理，那就按完整矩阵走，ManiSkill3 是省不掉的。
